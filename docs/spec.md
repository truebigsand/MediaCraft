# MediaCraft 技术规格与实测记录

本文档记录**设计定稿**与**在本机实测得到的结论**。凡是「实测」字样，都是在
`ffmpeg 8.1.2-full_build-www.gyan.dev`（Windows）+ RTX 5070 Laptop + Intel Arc 140T + Core Ultra 9 285H
上真跑过的结果，而不是照抄文档。

---

## 一、设计定稿

### 1.1 范围

| 项 | 定稿 |
|---|---|
| 用途 | 批量转码为主 + 单文件精调（预设快转与高级原生参数并存） |
| 执行位置 | **只驱动本机 ffmpeg**，与远程服务器无关（执行层已抽象，后续可扩展） |
| FFmpeg 来源 | 自动探测（设置 → PATH → 常见位置）+ 设置页可手动指定；不内置、不自动下载 |
| 参数作用域 | **每个文件持有完整的一套参数**（含各自的轨道选择）；面板顶部的「参数作用域」卡片始终写明当前参数作用在谁身上，默认勾选「改参数时同步到所有文件」（批量常态），关掉即逐文件精调 |
| 队列 | 排序、暂停（不派发新任务）、取消、持久化续跑、并发 1-8、失败跳过与重试 |
| 输出 | 命名模板 + 防覆盖自动序号 + 可选 `-y`；默认输出到源文件所在目录 |
| 界面 | 标签页（转码/队列/预设/设置）+ 可折叠日志面板；中文；浅色单主题；**无托盘**，关窗即退出 |
| 参数编辑 | 双模式：简单（0-100 滑块）⇄ 高级（原生参数），切换时双向换算避免跳变 |
| 字幕 | 轨道选择、烧入（libass 样式）、提取为 srt/ass/vtt、srt↔ass 转换、外挂字幕文件烧入 |
| 诊断 | 逐项进度 + 速度 + 剩余时间 + 完整命令行（可复制）+ 日志面板 + 开跑前预检 |

### 1.2 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | `net10.0-windows` + WPF | 本机 SDK 10.0.301；与既有工程一致 |
| MVVM | `CommunityToolkit.Mvvm`（唯一 NuGet 依赖） | 既有工程有先例；源生成器减少样板 |
| UI 库 | **不引第三方 UI 库** | 沿用桌面既有工程的视觉基线，避免额外依赖 |
| 视觉 | `#F5F6F8` 底 + 白卡片（`#DDD` / 圆角 6）+ 主色 `#2E7D32` | 与 TrayToolTemplate 系列一致 |
| 持久化 | `System.Text.Json` + `%AppData%\MediaCraft` | 与既有工程一致 |
| win32 互操作 | 无 | 不需要托盘与注册表（已去掉开机自启） |

### 1.3 从模板继承 / 明确偏离

继承：`net10.0-windows`、WinExe、`StartupObject`、`ApplicationIcon`、`SatelliteResourceLanguages=zh-Hans`、
单实例 Mutex + EventWaitHandle、静态 `AppLog`、`SettingsService`（500ms 防抖 + 退出强制保存）、
发布脚本产物落 `桌面\Claude Outputs\<App>\`、中文注释、file-scoped namespace、`sealed`、无版权头、不用 record。

偏离：**去掉 `UseWindowsForms` 与托盘**（关窗即退出）、**引入 CommunityToolkit.Mvvm**（界面复杂度远超托盘工具）、
**新增 `Views/`+`ViewModels/` 分层**、**新增 `--selftest` 无头自检模式**。

## 二、实测探测记录

### 2.1 本机编码器可用性（功能探测 = 真跑一帧，不是读 `-encoders`）

| 编码器 | 结果 | 编码器 | 结果 |
|---|---|---|---|
| `h264_nvenc` | ✅ | `libx264` | ✅ |
| `hevc_nvenc` | ✅ | `libx265` | ✅ |
| `av1_nvenc` | ✅ | `libsvtav1` | ✅ |
| `h264_qsv` | ✅ | `libaom-av1` | ✅ |
| `hevc_qsv` | ✅ | `av1_qsv` | ✅ |
| `vp9_qsv` | ✅ | | |

硬件加速方式：`cuda, vaapi, dxva2, qsv, d3d11va, opencl, vulkan, d3d12va, amf`。
AMF 虽然编译进来了且 `-hwaccels` 列出，但本机没有 AMD 显卡，`h264_amf` 功能探测失败——
**这正是「编译进去 ≠ 能跑」的实证，也是功能探测必须存在的理由**。

### 2.2 被实测推翻的两个假设（重要）

**假设一：H.264 NVENC 默认输出 High 4:4:4 Predictive，必须补 `-profile:v main`。**

在本机 ffmpeg 8.1.2 上**已不成立**：不补任何参数，`h264_nvenc` 与 `hevc_nvenc` 的输出实测都是
`profile=Main, pix_fmt=yuv420p`。旧结论来自 ffmpeg 6.1.1。

→ 因此预检**不硬编码这条规则**，而是按 ffmpeg 主版本条件触发：仅在 `MajorVersion < 7` 且
未指定 profile 时提示并补 `-profile:v main`。

**假设二：`subtitles` 滤镜可以用 `subtitles=C\:/path/file.srt` 或 `-/vf` 脚本文件传绝对路径。**

实测**都失败**（`Unable to parse "original_size" option value`）。

→ 唯一可用写法是**内层单引号 + 转义冒号**：

```
subtitles='C\:/Users/.../sub.srt':force_style='FontName=Microsoft YaHei,FontSize=24,...'
```

即 `FilterBuilder.EscapeFilterPath` 的实现。注意整个滤镜参数是**一个 argv 元素**（用 `ArgumentList` 传参，
不经过 cmd），所以这里的引号是给 ffmpeg 滤镜解析器看的，不是给 shell 看的。

### 2.3 硬解与软件滤镜的冲突（实测三态）

| 场景 | 命令形态 | 实测 |
|---|---|---|
| 纯显存链路（无滤镜 / 仅 `scale_cuda`） | `-hwaccel cuda -hwaccel_output_format cuda [-vf scale_cuda=W:H]` | ✅ 帧全程在显存 |
| 硬解 + 软件滤镜 | `-hwaccel cuda`（**不加** `output_format`，帧自动回读） | ✅ |
| 硬解 + `output_format cuda` + 软件滤镜 | 直接接 `subtitles` | ❌ `Impossible to convert between the formats ... src: cuda` |
| 硬解 + `output_format cuda` + 显式桥接 | `-vf "hwdownload,format=nv12,subtitles=..."` | ✅ 桥接可行 |

选择策略：**有软件滤镜时不加 `-hwaccel_output_format`**（最简且实测可用），
仅在「无软件滤镜」时才用显存链路；NVENC + cuda 下的缩放走 `scale_cuda`（判定条件与
预检里「是否算软件滤镜」的判定必须一致，否则会给用户误导性提示——这条踩过）。

QSV 侧同构：`-hwaccel qsv`（回读）或 `-hwaccel qsv -hwaccel_output_format qsv -vf "hwdownload,format=nv12,..."`，均实测可用。

### 2.4 失败残留（实测）

ffmpeg 失败时会留下 **0 字节同名输出文件**。因此：

- 成败只看**进程退出码**（不能按「文件是否存在」判断——最初的自检脚本正是这么写错的）
- 失败后删除残留，但**仅限运行前不存在的文件**（否则会误删用户原有同名文件）

### 2.5 内封字幕烧入

`subtitles` 滤镜读的是**文件**；对多轨容器用 `si` 参数指定轨道的行为跨版本不一致。
本工具统一**先把内封轨抽成临时文件再烧入**（这条路径实测可用），任务结束清理临时文件。

### 2.7 参数作用域的实现与踩过的坑

「每文件独立参数」是设计选择，但它带来一个很容易踩的坑：**参数面板编辑的到底是谁？**

- 选中文件时编辑该文件；未选中时编辑「新文件默认参数」模板。
  最初添加文件后不自动选中任何文件，于是用户拖质量滑块 → 改的是模板 → 列表里的文件毫无变化，
  表现就是「质量滑块无效」。现在：**添加文件后自动选中第一个**，并且面板顶部常驻作用域卡片写明
  「当前参数作用于全部 N 个文件」或「只作用于 X」。
- 同步到所有文件时**只复制标量参数**（`CopyScalarsFrom`），不碰轨道列表：轨道选择按流索引走，
  索引因文件而异，必须留在各文件自己的轨道对象上。
- 「应用到全部」走 `CopyScalarsFrom` + `InitializeTracksFrom`（按目标文件重建索引）
  + `ApplyTracksFrom`（**按位置**把轨道动作搬过来）。
  早期版本漏了最后一步，重建轨道时把「烧入字幕」这类动作打回了默认「直通」——现在自检里有断言锁住。
- 质量提示文本（`-cq 23 -preset p5`）在**任何**参数变化时都刷新。早期只在「编辑模板」分支里刷新，
  选中文件时拖滑块提示不动，用户唯一能看到的反馈是假的，进一步加重了「滑块无效」的错觉。

### 2.9 最严重的一次错误：手写的「容器 × 编码」兼容表

最初这张表是按经验手写的，结果把 `pcm_s24le` 在 MP4 里判成**非法**。后果不是报错，而是：

1. 预检「贴心地」把用户的**无损 PCM 直通**改成**有损 AAC 192k**
2. 用户每次想改回直通，预检都会再改回去——因为表认为它非法
3. 用户既丢了画质，又无法阻止，且**看不到任何异常**（界面只显示「已自动处理」）

这比直接报错糟糕得多。用真实 ffmpeg 逐个探测后的事实是：

```
pcm_s24le -c copy → mp4      ✅   （写成 ipcm 采样项）
pcm_s24le -c copy → mkv      ✅
pcm_s24le -c copy → mov      ✅
aac → webm                   ❌  「Only VP8 or VP9 or AV1 video and Vorbis or Opus audio …」
mp3 → m4a(ipod)              ❌  「Could not find tag for codec mp3」
av1 → mov                    ❌  「av1 only supported in MP4 and AVIF」
mov_text → mkv               ❌  「Subtitle codec mov_text is not supported」
```

现在的做法：

- 表按**实测结果**重写，并在代码注释里写明「来自实测，不是按经验写的」
- PCM 装 MP4/MOV 从「错判为非法并强制重编码」改为**仅提示兼容性**，绝不动用户的直通选择
- 自检新增「**容器兼容性矩阵与 ffmpeg 实测一致**」用例：把 117 个「容器 × 编码」组合
  逐个真跑一次，表与实测不一致就失败。规矩从此是：**这张表只能由实测守住，不能靠记忆和推测**

注意两套命名：表里用 ffprobe 的 `codec_name`（运行时拿 `track.SourceCodec` 比对），
探测时要用 ffmpeg 的**编码器**名——同一个东西两种叫法（`srt` = `subrip`）曾经让自检报了一次假警报。

### 2.14 两遍编码：谁能用、以及「命令成功」不等于生效

两遍编码（`-pass 1` 分析 + `-pass 2` 编码）在 ffmpeg 里由编码器实现，逐个实测：

| 编码器 | `-pass` 效果 | 统计文件 |
|---|---|---|
| `libx264` / `libx265` / `libsvtav1` / `libaom-av1` | 生效 | 7246 / 9853 / 4556 / 19520 字节 |
| `h264_nvenc` / `hevc_nvenc` / `h264_qsv` | **静默忽略** | 0 字节（命令返回成功，也没有任何告警） |

所以判定标准**不能是退出码**，而是「统计文件里有没有内容」——这正是自检 [4c] 用例的做法：
逐个编码器跑一遍 pass 1，比较统计文件是否非空与表里的 `SupportsTwoPass` 是否一致。

另一个实测结论：**目标码率 + CRF 组合下第二遍会直接失败**（x264 退出码 127、x265 退出码 183），
所以界面把两遍编码放在「目标码率」模式下，预检在质量优先模式或硬件编码器上会关闭它并说明原因；
界面里的说明文字是按当前编码器**推导**的（与 2.7 的轨道提示同一模式），
不会出现「选项被关掉但看不到原因」。

### 2.13 音频编码的两套命名（差点又是一次静默重编码）

容器的音频白名单要跟 `track.SourceCodec`（ffprobe 的 `codec_name`）比对，
而界面下拉与 `-c:a` 用的是 ffmpeg 的**编码器 id** —— 有三个编码器两边名字不同：

| ffprobe codec_name | ffmpeg 编码器 id |
|---|---|
| `opus` | `libopus` |
| `mp3` | `libmp3lame` |
| `vorbis` | `libvorbis` |

最初白名单里写的是编码器 id，于是「MKV 里的 opus 直通」被判成不兼容 →
预检把它**强行重编码成 AAC**。这与 2.9 的 PCM 事件是同一类错误：**静默的有损重编码，用户既丢画质又无法阻止**。
（有意思的是，正是当时新加的行内提示把这条错误判断显示了出来，才让它暴露的。）

现在：白名单统一按 ffprobe 规范名书写，`IsAudioCodecCompatible` 两侧都做归一化
（`CanonicalAudioCodec` / `AudioEncoderIdFor`），自检里有专门的用例锁住
「两种写法必须得到同一判定」以及「opus 在 MKV 可直通、在 MOV 不行」。

注意探测/构造时的细节：多音轨探测若把规范名当编码器名传给 `-c:a`，
会命中 ffmpeg 的**实验性原生编码器**并报 `experimental codecs are not enabled` ——
必须用 `AudioEncoderIdFor` 换回编码器 id。

### 2.12 容器对**多条音轨**的支持（实测）

| 容器 | 多条音轨 | 实测 |
|---|---|---|
| mp4 / mkv / mov / webm / **m4a** / opus(ogg) | ✅ | 3 条音轨全部写出并保留 |
| **mp3** | ❌ | `Exactly one MP3 audio stream is required.` |
| **flac** | ❌ | `Exactly one FLAC audio stream is required.` |
| **wav** | ❌ | `wav muxer does not support more than one stream of type audio` |

这不是理论问题：本机日志里就有一条真实失败 —— 用 3 条音轨的 BLU-RAY rip 输出 WAV，
**0.1 秒就失败**（`Conversion failed!`，muxer 直接拒写），只保留一条后 11 秒成功。
所以预检补了一条规则拦下这种组合：

- 触发条件：容器 `MaxAudioStreams = 1`（mp3/flac/wav）且保留的音轨多于 1 条
- 处理：**错误、只拦不修** —— 自动丢掉用户勾选的音轨属于静默数据丢失，必须由人决定保留哪一条
- 提示文案带可操作信息：「WAV 只能写入 1 条音轨，当前有 3 条被保留（音轨 #1、#2、#3）。请只勾选一条，或把输出容器改成 MKV / MP4 / M4A」
- 自检的 135 组合矩阵校验现在也覆盖多音轨能力（用容器自己支持的编码器 × 3 条音轨探测，
  断言「能否写入」与 `MaxAudioStreams` 一致）

注意规则顺序：先有「纯音频容器装不下视频流 → 自动丢弃视频并把容器换成合适的音频容器」，
再判断音轨条数。两者是串联的 —— 若在视频容器 + flac 容器上直接判条数，
会先被前一条规则把容器换成 m4a（支持多音轨）而永远触发不到，自检里为此专门标注了这一点。

### 2.10 音频码率：哪些编码器需要设、哪些设了也没用

| 编码器 | `-b:a` 是否有效 | 实测结论 |
|---|---|---|
| `pcm_s24le` | ❌ 完全无效 | 不设 / 192k / 9999k 三份产出**字节完全一致**（264,702 字节） |
| `flac`（无损压缩） | ❌ 无效 | 不设 vs 100k，字节完全一致 |
| `aac`（有损） | ✅ 有效 | 不设 18,786 字节 vs 320k 34,323 字节 |
| `ac3`（有损，固定档位） | ✅ 有效但仅限档位 | 200k → 192k、1000k → 640k，**ffmpeg 静默取整，不报错** |

- **PCM 码率 = 采样率 × 位深 × 声道数**：44100×24×2 = 2116 kbps、×6 = 6350 kbps，
  与 ffprobe 报告值精确吻合。想控制 PCM 体积只能改位深、声道、采样率，跟码率参数无关。
- 因此界面按编码器切换码率控件的形态；**无损编码器不传 `-b:a`**（传了只会误导用户）。

**顺带挖出的隐藏 bug**：`TargetChannels` 选项从第一版起就没生效过——命令里写的是 `-ac:0`，
流说明符被理解为「输出流 0」（那是视频流）从而被 ffmpeg 忽略；正确写法是 `-ac:a:0`。
一直没暴露的原因是**没有测试覆盖这条路径**，现在自检里有断言锁住 `-ar:a:0` / `-ac:a:0` 与产出的采样率/声道。

### 2.8 其他实测事实

- `ffprobe` 的 JSON 里 `bit_rate` / `duration` / `sample_rate` 等字段是**字符串**，解析时需 `AllowReadingFromString`
- `-progress pipe:1` 的 `out_time` 是权威时间戳；`out_time_ms` 实际是**微秒**（ffmpeg 的历史遗留命名）
- 字幕格式转换显式带 `-f`（`srt`/`ass`/`webvtt`），不依赖扩展名推断
- 面板宽 470px 时列表 9 列会横向滚动（默认窗口 1240×800；最大化后完整显示）

## 三、命令构造规则

### 3.1 视频编码参数

| 模式 | 构造 |
|---|---|
| 简单 | `{QualityParam} = round(比例(滑块) × 质量上限)` + `{PresetParam} = 滑块映射的 preset` |
| 高级·质量优先 | `{QualityParam} = 指定值`（越界自动 clamp 并提示） |
| 高级·目标码率 | `-b:v Nk` [+ `-maxrate` `-bufsize`] [+ NVENC 的 `-rc cbr/vbr`] |
| 高级附加 | preset / tune / profile / level / GOP / pix_fmt（显存链路下**不传** `-pix_fmt`） |

质量锚点（滑块 0-100 → 占上限比例）：`100→0.274`、`90→0.353`、`75→0.451`、`60→0.529`、`50→0.588`、`25→0.745`、`0→1.0`。
理由：NVENC 的 `-cq` 与 x264/x265 的 `-crf` 同为 0-51 且语义一致（越小越好），同一套锚点对两者都成立，
且滑块 75 正好落在经典 CRF/CQ 23。零界 63 的编码器（SVT-AV1 / libaom）按同一比例映射。

### 3.2 流映射

- 视频：`-map 0:<视频流索引>`（`VideoMode=Drop` 时不映射）
- 音频：按选择顺序逐个 `-map`，编码参数**按输出序号**逐个指定（`-c:a:0` / `-b:a:1`…），
  避免多轨互相干扰
- 字幕：`Copy` 才映射；`Burn` 通过滤镜；`Extract` 走独立步骤；`Drop` 不映射
- 容器决定字幕编码：能 `copy` 就 copy，MP4/MOV 退回 `mov_text`（仅文本字幕）

### 3.3 步骤拆分

一个任务可展开为多个 ffmpeg 调用，**顺序执行**：

1. `Prepare`：需要烧入内封字幕时，先抽成临时文件（不产出用户文件）
2. `Transcode`（或 `SubtitleConvert`）：主步骤，带进度
3. `ExtractSubtitle`：每个选了「提取」的字幕轨一个附加步骤

总进度 = 已完成步骤 + 当前步骤进度，按**可跟踪步骤**（有时长信息的）折算。

## 四、预检规则清单

能自动修的一律修掉并在界面与日志里留下记录；不能修的拦下不跑。

| # | 触发条件 | 级别 | 处理 |
|---|---|---|---|
| 1 | 编码器在本机功能探测失败 / 不存在于该 ffmpeg | 错误 | 拦下 |
| 2 | 硬解方式本机不支持 | 警告 | 自动改为 CPU 软解 |
| 3 | 视频直通 + 有缩放或烧字幕 | 警告 | 自动改为重新编码 |
| 4 | 烧入图形字幕（PGS/DVD） | 错误 | 拦下（需 OCR） |
| 5 | 外挂字幕文件不存在 | 错误 | 拦下 |
| 6 | 提取图形字幕为文本 | 警告 | 该轨自动改为丢弃 |
| 7 | 目标分辨率超出编码器上限 | 警告 | 自动按比例收缩 |
| 8 | 容器装不下所选编码格式 | 警告 | 自动改为 MKV |
| 9 | 纯音频容器 + 视频流 | 警告 | 自动丢弃视频（只出音频） |
| 10 | 音频编码/直通与容器不兼容 | 警告 | 自动改编码（AAC 优先）或转码 |
| 11 | 字幕无法内封到该容器 | 警告 | 该轨自动改为丢弃 |
| 12 | 源 10bit 但编码器不支持 | 警告 | 提示会丢位深 |
| 13 | 源是 HDR | 警告 | 提示未做色调映射，SDR 上可能发灰 |
| 14 | 帧率非法 / 与源差异过大 | 错误/警告 | 拦下 / 提示 |
| 15 | 质量值超出编码器范围 | 警告 | clamp |
| 16 | 老版本 ffmpeg（<7）的 NVENC profile 兜底 | 提示 | 自动补 `-profile:v main` |
| 17 | **输出路径 = 源文件路径** | 错误 | 拦下（防覆盖源文件） |
| 18 | 输出目录不存在 | 提示 | 自动创建；创建失败则拦下 |
| 19 | 硬解 + 软件滤镜 | 提示 | 说明帧会回读（自动处理，无需干预） |
| 20 | PCM 直通到 MP4/MOV | 提示 | **只提示不改动**：ffmpeg 能写，但部分硬件播放器不认 |

## 五、线程与进程纪律

- 队列任务的**可见状态只在 UI 线程修改**，后台流程统一经 `Dispatcher.BeginInvoke` 转发
- 耗时操作（ffprobe / ffmpeg / 编码器探测）全在后台；启动时窗口先出来，探测异步进行
- 编码器功能探测并发上限 4（同时起太多 ffmpeg 会互相抢资源导致误判）
- 文件分析并发上限 4
- 取消 = 杀进程树 + 清理残留；`-nostdin` 保证 ffmpeg 不去读标准输入
- 所有 ffmpeg 调用都用 `ProcessStartInfo.ArgumentList`（不拼命令行字符串），路径中的空格/引号/中文无需手工转义

## 六、自检覆盖矩阵

`--selftest all` = 46 项，其中：

**纯逻辑（不需要 ffmpeg，CI 里跑 `logic` 模式）**

2. 轨道意图归纳（混合字幕动作 → 烧入第一条；混合音轨动作 → 退化为直通）
3. 意图套用（FirstOnly 语义：第一条烧入、其余内封；轨道数量不变）
4. JSON 三种结构解析（包装 / 数组 / 单对象）+ 往返一致 + 非法输入处理
5. 参数深拷贝独立性（每文件独立参数的基础）

**环境探测**

**兼容性矩阵校验**

**转码矩阵（每项真跑并用 ffprobe 校验产出编码/分辨率/时长/像素格式/profile/音轨数）**

## 七、测试与验证方法（本项目实际用到的）

| 手段 | 用途 |
|---|---|
| `--selftest` | 用**生产代码路径**跑真转码矩阵，ffprobe 校验产出 |
| UI Automation（PowerShell） | 真实点击按钮/切换标签页/选中列表行，验证界面到引擎的链路 |
| 截图（PrintWindow） | 确认渲染结果 |
| 日志（含绑定错误） | 排查静默失败 |
| 预设/参数纯逻辑自检 | 不依赖 ffmpeg 的逻辑回归 |

注意：UI 自动化脚本里**不能出现中文字面量**（UTF-8 无 BOM 的 ps1 会被 PS 5.1 按 GBK 读，
中文字符串会变乱码导致匹配失败），中文参数一律用环境变量传入。
